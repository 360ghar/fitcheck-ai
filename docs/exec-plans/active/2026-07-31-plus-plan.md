# Plan: Introduce the $10 Plus plan

Status: active
Started: 2026-07-31
Owner: agent

## Goal

Ship a third subscription tier, **Plus** at $10/mo (or $100/yr), sitting between
Free and Pro. Plus unlocks the **same features** as Pro — virtual try-on,
analytics, calendar planning, priority support — but with lower monthly usage
limits. This gives price-sensitive users a paid entry point without splitting
the feature matrix, so entitlement stays a single predicate and only the quota
lookup becomes tier-aware.

Plus limits: 100 item extractions, 350 outfit visualizations, 2,000 embeddings
per month; 30 photoshoot images per day.

## Non-goals

- Per-feature entitlement gating (Plus is feature-equivalent to Pro by design).
- Changing the referral credit, which still grants 1 month of **Pro**.
- Enabling paid plans on iOS — `EnvConfig.paywallEnabled` keeps monetization
  CTAs off on iOS for v1 (App Store Guideline 3.1.1), and the store listings
  keep their "free, no IAP" posture. *(Superseded 2026-08-01: mobile IAP shipped —
  see `docs/exec-plans/completed/2026-08-01-mobile-iap-subscriptions.md`. `EnvConfig.paywallEnabled`
  now defaults ON on all platforms and iOS buys via StoreKit.)*
- Migrating the `grant_free_pro_month.py` / `revert_expired_pro_trials.py`
  campaign scripts, which remain Pro-specific.

## Acceptance criteria

- [x] `PlanType` gains `plus_monthly` / `plus_yearly` on backend, web, Flutter.
- [x] `get_plan_limits` is a 3-way lookup; `is_paid_plan` treats Plus as entitled.
- [x] `plan_display_name` replaces the `startswith("pro")` / `is_pro` ternaries
      so quota messages say "Plus" instead of mislabelling it "Free".
- [x] `/plans` returns three tiers, each computing its own `savings_yearly`.
- [x] Checkout maps every paid plan to an explicit Stripe price ID — no
      silent "anything not yearly = monthly Pro" fallback.
- [x] Yearly period math covers any `*_yearly` plan (was `PRO_YEARLY`-only).
- [x] Web pricing shows 3 aligned, equal-height cards with Plus highlighted.
- [x] Flutter paywall offers Plus and Pro, each monthly + yearly.
- [x] Docs/specs reflect the three tiers; stale $9.99 / "unlimited" figures fixed.
- [x] A Plus subscriber still has an in-app path to Pro on both web and Flutter
      (upgrade CTAs gate on `can_upgrade`, not on `!is_paid_plan`), and is never
      offered the tier they are already on.
- [x] Pro users at their cap are not told to "upgrade to Pro".
- [ ] **Manual (human):** create the Plus monthly ($10) and yearly ($100) price
      objects in Stripe and set `STRIPE_PLUS_MONTHLY_PRICE_ID` /
      `STRIPE_PLUS_YEARLY_PRICE_ID` in `backend/.env`. Until then, Plus
      checkout returns "Stripe price not configured".

## Decision log

| Date | Decision | Why |
|------|----------|-----|
| 2026-07-31 | Plus = same features as Pro, lower limits | Keeps entitlement a single boolean; avoids a per-feature gating refactor across three clients. |
| 2026-07-31 | `is_pro_plan` delegates to `is_paid_plan` rather than being renamed everywhere | `SubscriptionResponse.is_pro` is a wire field consumed by web + Flutter; changing its meaning (paid vs strictly-Pro) is backward compatible, renaming it is not. |
| 2026-07-31 | Explicit plan→price-ID dict in checkout | The old `else` branch would have charged Plus buyers the $20 Pro monthly price. |
| 2026-07-31 | Period math keys off the `_yearly` suffix | The old `== PRO_YEARLY` check would have billed a Plus-yearly customer for a year and granted one month. |
| 2026-07-31 | `PLAN_PRICES` + shared `paidPlanFeatureBullets()` on web | Prices and the Pro feature list were duplicated across 3+ files; new tier would have tripled the drift. |
| 2026-07-31 | No DB migration beyond a column comment | `plan_type` is `VARCHAR(20)`; both new values fit. |
| 2026-07-31 | Added a second predicate, `can_upgrade` / `selectCanUpgrade` / `controller.canUpgrade`, alongside the paid check | With only two tiers, "has paid features" and "is on the top tier" were the same question, so every upgrade CTA was gated on `!isPro`. With Plus in the middle that stranded Plus subscribers: the web rate-limit dialog hid its upgrade button, `SubscriptionPanel` hid all plan cards, and `subscription_page.dart:58` hid the entire Flutter upgrade section — a Plus user had no in-app route to Pro. Entitlement and upsell are now separate questions. |
| 2026-07-31 | Limit messages only append "Upgrade to Pro for more!" when a higher tier exists | Pro users at their cap were being told to upgrade to the plan they are already on. |
